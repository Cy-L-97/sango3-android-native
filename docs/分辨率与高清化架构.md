# 分辨率与高清化架构

> 状态：**已定稿（M1）** —— 本文是长期规范，后续所有渲染/UI/素材相关代码都必须遵守。
> 起因：用户要求"开发过程要匹配现在的标准，至少支持 2K；素材高清化放最后做，通过素材文件替换实现"。

---

## 一、铁律（三条）

1. **逻辑坐标与物理分辨率彻底解耦。**
   所有玩法逻辑、界面布局、点击命中判定，一律使用 **640×480 逻辑坐标**；
   代码里**不得出现**任何物理像素常量（2560、1440 等）。

2. **物理分辨率只在一个地方出现：视口变换层（`render.c`）。**
   换分辨率 = 换一个缩放系数，不改任何业务代码。

3. **素材按 `1×/2×/3×/4×` 分级，引擎按输出分辨率自动选档。**
   没有高清包时回退到 1× + 缩放（今天就能玩）；高清包做完丢进目录即生效，
   **不用改代码、不用重编译、不用重打包**。

## 二、事实基线（全部来自本机正版文件的实测，非推测）

| 事实 | 证据 | 影响 |
|---|---|---|
| 逻辑坐标空间 = **640×480** | `Setting\Menu.ini` 根窗口 `Range = 0, 0, 640, 480`；全部坐标最大值 640/480 | 架构锚点 |
| 逻辑坐标与素材像素 **1:1** | `Menu.ini` 有 `Range = 105, 107, 433, 34`，而素材 `Shape\MM\Base\Setting09.SHP` 实测正是 **433×34**；另有 `Range = 91, 65, 464, 31` ↔ 464×31 素材 | **不需要 DPI 换算表**，界面图纸可直接当布局用 |
| 分辨率**无**数据层配置 | 全文检索 `800/600/640/480/1024/screen/width/height/fullscreen` 等关键字：**0 命中** | 原版分辨率硬编码在 exe 内；我们能自由定义，不受原版限制 |
| 字体是三档点阵位图 | `Font\Ch01-14.fnt` / `Ch01-16.fnt` / `Ch01-20.fnt`（中文 14/16/20 px）、`Ch02-*`、`En01-*`、`En02-*`、`Font\Default.idx`(38000B)、`Setting\AllFont.dat`(38003B)、`Setting\Font001.ini`/`Font002.ini`(各 1069B) | 2K 下若直接放大必糊 → 见第六节 |
| 界面文本用 `Font = 0/1/2` 声明 | `Menu.ini` 中每个文本元素都有 `Font = N`，取值只有 0/1/2 | 大概率对应 14/16/20 三档字号，待解析 `Font00x.ini` 确认 |

> 顺带修正：早期方案文档中写的"固定 800×600"是错的，已按实测改为 640×480。

## 三、坐标系与变换

```
                  ┌──────────────────────────────────────────┐
   逻辑空间         │  640 × 480（原版界面坐标空间）             │
   (布局/玩法/命中)  │  所有 UI 布局直接取 Menu.ini 的 Range 值    │
                  └──────────────────┬───────────────────────┘
                                     │  sango3_viewport_init()
                                     │  scale = min(out_w/640, out_h/480)
                                     ▼
                  ┌──────────────────────────────────────────┐
   物理空间         │  out_w × out_h（1080p / 2K / 4K / 手机）  │
   (像素输出)       │  内容居中，四周留边填充背景色              │
                  └──────────────────────────────────────────┘
```

坐标变换接口（双向，UI 命中测试必需）：

| 函数 | 用途 |
|---|---|
| `sango3_viewport_init()` | 算缩放系数与内容矩形 |
| `sango3_logical_to_physical()` | 触摸/鼠标坐标反查、物理层 UI 定位 |
| `sango3_physical_to_logical()` | 点击命中：物理坐标 → 逻辑坐标 → 查 Menu.ini 控件 |
| `sango3_pick_asset_tier()` | 按缩放系数挑素材档位 |

## 四、缩放滤镜策略

| 滤镜 | 实现 | 何时用 |
|---|---|---|
| `NEAREST` | 最近邻 | 整数倍缩放（像素完美派）。1440p 恰好 ×3，结果最锐 |
| `BILINEAR` | 双线性 | 非整数倍时的"平滑"选择，但像素画会糊，仅作对照 |
| `SHARP`（默认） | **整数预放大（最近邻）+ 双线性收尾** | 通用推荐：整数倍时退化为纯最近邻（完全一致），非整数倍时保住像素块又抹平台阶 |

`SHARP` 的数学性质：`k = floor(scale)`；当 `scale` 为整数时 `k = scale`、小数部分为 0，
**结果与 NEAREST 逐像素相同**。已在 1440p（×3.000）实测验证。

## 五、分辨率目标与缩放系数

4:3 内容放到 16:9 / 21:9 / 手机长屏，两侧必然留边（pillarbox）。实际数值：

| 物理分辨率 | 屏比 | 缩放 | 4:3 内容矩形 | 两侧留边 | 素材档位 |
|---|---|---|---|---|---|
| 640×480 | 4:3 | ×1.000 | 640×480 | 0 | 1× |
| 1280×720 | 16:9 | ×1.500 | 960×720 | 各 160 | 1× |
| 1920×1080 | 16:9 | ×2.250 | 1440×1080 | 各 240 | 2× |
| 2560×1440 | 16:9 | **×3.000** | 1920×1440 | 各 320 | 3× |
| 2560×1600 | 16:10 | ×3.333 | 2133×1600 | 各 213 | 3× |
| 3440×1440 | 21:9 | ×3.000 | 1920×1440 | 各 760 | 3× |
| 3840×2160 | 16:9 | ×4.500 | 2880×2160 | 各 480 | 4× |
| 3200×1440（手机） | 20:9 | ×3.000 | 1920×1440 | 各 640 | 3× |

**交付标准：最低支持 2560×1440（2K），设计上限 4K。**

### 宽高比策略（`Sango3Aspect`）

| 模式 | 行为 | 用在哪 |
|---|---|---|
| `PILLARBOX`（默认） | 保 4:3，两侧留边 | PC 桌面、菜单/内政界面 |
| `STRETCH` | 拉伸铺满 | 仅作对照（会变形，不推荐） |
| `EXTEND`（M4 追加） | **横向扩展视野**：逻辑世界层比 640 宽，UI 锚定在 4:3 安全区内 | 手机长屏的地图/战场 —— 这是真正利用宽屏的做法 |

> 手机 20:9 上 pillarbox 两侧各留 640px 黑边，观感很差。
> 因此 M4 安卓适配时，**地图与战场层必须走 `EXTEND`**：世界层按实际宽度渲染多出来的区域，
> UI 层保持 4:3 居中安全区。`Sango3Viewport` 需要增加"分层视口"能力（每层独立 aspect 策略）。

## 六、文字与 UI 的高清策略（2K 清晰度的真正关键）

**问题**：原版中文是 14/16/20 像素的点阵位图。在 2K（×3）下直接放大，14px → 42px，
锯齿与模糊都会非常明显。**这是"画面里唯一放大后一定难看的东西"。**

**方案：双字体路径，默认走原生矢量。**

| 模式 | 做法 | 适用 |
|---|---|---|
| `pixel`（像素完美） | 原版点阵按 1×/2×/3× **整数倍最近邻**绘制 | 整数倍缩放、怀旧口味 |
| `native`（默认） | 用矢量字体（内置可自由分发的开源中文字体）**按目标物理尺寸直接渲染**，字号 = 原版字号 × scale；布局仍取 `Menu.ini` 的坐标与控件宽度 | 2K / 4K / 手机 |

需要补的三件事：
1. 解析 `Font001.ini` / `Font002.ini` / `AllFont.dat` / `Default.idx`，确定 `Font = 0/1/2` 与字号的对应关系；
2. 写**字形度量适配层**：矢量字体的字宽 ≠ 原版点阵字宽，必须用 Menu.ini 的控件宽度做约束，
   超宽时自动缩字号或换行，避免文字溢出原版控件；
3. 字体授权合规：内置字体须为可自由分发的开源字体（或由用户自备），**不得内置原版 `.fnt`**。

同样的道理适用于**所有 UI 边框、分隔线、选中框**：
它们应由 `sango3_fill_rect()` 这类**物理分辨率直绘**接口画出（任何分辨率下都是 1 像素锐利），
而不是把 640×480 的位图整帧放大。演示程序的边框与刻线就是这么画的。

## 七、素材分级（Asset Tier）规范

### 7.1 目录约定与查找顺序

对逻辑路径 `Shape\Portrait\Portrait001.SHP`，引擎按下列顺序查找，**第一个命中的生效**：

```
1. Shape@4x\Portrait\Portrait001.SHP     ← 4× 高清档（仅当 scale>=4）
2. Shape@3x\Portrait\Portrait001.SHP     ← 3× 高清档（仅当 scale>=3）
3. Shape@2x\Portrait\Portrait001.SHP     ← 2× 高清档（仅当 scale>=2）
4. Shape\Portrait\Portrait001.SHP        ← 1× 覆盖档（★ 第三方"修复+增强补丁"已在此生效）
5. Sango3.PAK 内的 Shape\Portrait\...    ← 原版兜底
```

- 第 4 条**已实测有效**：游戏目录 `Setting\General01.ini`(130,585 B) 比 PAK 内(130,568 B) 更新，
  证明外置覆盖机制真实存在，第三方补丁正是这么工作的。我们的引擎沿用同一约定，互不冲突。
- 高清包只需要放**它改动了的文件**，未放的文件自动回退到下一档。

### 7.2 素材包清单 `pack.json`

```json
{
  "name": "Sango3 HD Pack",
  "tier": 2,
  "scale": 2.0,
  "generator": "Real-ESRGAN x4plus + 手工重绘 UI",
  "coverage": ["Shape/Portrait/*", "Shape/MM/*"],
  "exclude": ["Shape/Font/*"],
  "source": "本机正版 Sango3.PAK（Steam）",
  "note": "仅含由本机正版素材超分/重绘所得文件，不含原版文件本身"
}
```

版本控制：`.gitignore` 已排除 `*.shp` / `assets/hd/`，**高清包不进仓库**（体积大 + 版权边界），
两台机器各自本地放置；仓库内只保存 `pack.json` 与生成脚本。

### 7.3 为什么这样能满足"高清化最后做"

因为高清化被定义为**一次纯资源替换**，不触碰任何代码：

- 现在：tier 1 素材 + `SHARP` 滤镜 → 2K 下可玩，画面风格与原版一致（干净的锐化放大）；
- 以后：把高清包丢进 `Shape@2x/` → 同一个引擎自动选到 2× 档，1:1 渲染，**零代码改动**；
- 引擎侧需要提前做好的只有一件事：**图元级按档绘制**（见第八节路径 B）。

## 八、两条渲染路径（重要区分）

| | 路径 A · 整帧放大 | 路径 B · 图元级原生渲染 |
|---|---|---|
| 做法 | 640×480 逻辑画布 → 整帧缩放到物理分辨率 | 直接在物理分辨率上绘制每个图元，按 `scale` 变换坐标，按档位取素材 |
| 状态 | **已实现**（`render.c`，M1 验证通过） | **M2 目标**（接口已预留：`sango3_logical_to_physical` / `sango3_pick_asset_tier`） |
| 2K 观感 | 细节有损（尤其文字与细边框） | 1:1 清晰（tier 匹配时零重采样） |
| 高清包收益 | 无（高清素材也被整帧缩掉） | 完全发挥 |
| 用途 | 立即可跑、离线像素校验、降级兜底 | 正式运行时路径 |

> **性能前提**：整帧放大（2560×1440 = 369 万像素/帧）在 CPU 标量代码里只有几帧/秒，
> 远达不到 60fps。`render.c` 是**参考实现 / 离线验证器**；
> 运行时必须把这一步交给 **GPU**（一次纹理上传 + 硬件缩放，`SDL_RenderCopy` 或 OpenGL ES 等价变换），
> 算力开销可忽略。两条路径在 GPU 上的实现方式不同，但坐标变换公式完全一致 —— 复用 `render.c` 的数学。

## 九、平台适配

| 平台 | 要点 |
|---|---|
| Windows | 声明 DPI-aware；按显示器原生分辨率开窗；全屏时用显示器当前模式；支持无边框窗口缩放（缩放时只重算视口） |

## 十、与 5 项需求的关系

**全部不受影响，而且因为高分辨率反而更好落地：**

| 需求 | 与分辨率的交互 |
|---|---|
| ① 将领自动升级 | 纯逻辑，无渲染关系 |
| ② 士兵上限 1000 | 同屏 2000 兵是**性能**问题，不是分辨率问题；分辨率提高会加重 GPU 负担，M4 需实测 |
| ③ 必杀技无上限 | 必杀技选择界面需要扩容 → **正好用新布局系统按 2K 重排**，不受原版 640×480 控件尺寸束缚 |
| ④ 武力≥80 自动学必杀技 | 纯数据/逻辑（目标名单已产出：34 名武将 + 4 只野兽按规则排除） |
| ⑤ 素材高清化 | 就是本文第七节的素材分级机制 |
