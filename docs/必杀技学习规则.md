# 必杀技学习规则（第 3、4 项需求合并规范）

> 状态：**已定稿（M1）**。本文是长期规范，引擎实现必须遵守。
> 口径来源：用户 2026-09-13 最终确认 ——「**判断标准是武将当前的攻击力是否大于等于 80**，
> 低于 80 的武将通过装备把攻击力提升到 80 以上后，也会自动学习必杀技。」

---

## 一、为什么这个口径改变了实现方式

最初的实现设想是「M0 生成一份静态名单，开局一次性补数据」。**这是错的**，因为：

- 同一名武将，**换一把武器**就从「不达标」变成「达标」；
- 武器会在游戏过程中被买卖、缴获、更换、卸下；
- 因此不存在一份固定名单能表达「谁能学必杀技」。

数据给出了量级上的证明：

| 类别 | 含义 | 人数 |
|---|---|---|
| **A** | 基础武力 ≥ 80，**开局即达标** | **34** |
| **B** | 基础 < 80，但靠**初始自带武器**顶到 ≥ 80 | **0** |
| **C** | 基础 < 80，**换更强武器后即可跨过 80** | **184** |

> B = 0 说明：原版初始装备数据里，没有人靠自带武器跨过门槛。
> C = 184 说明：**如果你的规则只覆盖 A 的 34 人，就漏掉了几百人的动态情形** —— 这正是本次修正的核心。

**结论：判定必须在运行时进行，是「事件驱动的规则」，不是「开局补丁数据」。**

## 二、数据事实（全部实测，非推测）

### 2.1 攻击力公式

```
当前攻击力 = 基础武力(General01.ini : Strength)
           + 武器加成(Thing.ini : Type=2 物品的 Increment 字段)
```

### 2.2 装备槽与加成的对应关系

`General01.ini` 每名武将有三个装备槽，**存的是物品名字符串**（不是索引）：

| 槽位字段 | 对应物品 Type | 加成字段 `Increment` 的含义 | **是否影响攻击力** |
|---|---|---|---|
| `Weapon` | 2 · 武器 | 武力上升 **+1 ~ +20** | ✅ **计入** |
| `Book` | 3 · 书 | 智力 / 技力上限 / 体力上限（逐件不同） | ❌ 不计入 |
| `Horse` | 4 · 马 | 速度上升（部分带特性位） | ❌ 不计入 |

> 书与马**不影响攻击力**，因此不参与本条判定。这是逐件核对 `Statement` 文本确认的，
> 例如：`青龍偃月刀 / 武力上昇 10 點，使用等級 20`、`青囊書 / 體力最大值上昇 30 點`、
> `赤兔馬 / 速度上昇 8 點`。

### 2.3 武器加成分布（41 件武器）

| 加成 | 代表武器 |
|---|---|
| +1 ~ +3 | 吳鉤、紅櫻槍、眉尖刀 / 飛刀、桃木劍 / 青銅劍、三叉戟、大斧 |
| +4 ~ +7 | 銅長刀、流星鎚 / 鐵鉞戟、狼牙棒 / 月牙戟、鐵蒺藜骨朵 / 繡花鎚、雙股劍 |
| +8 ~ +10 | 青龍刀、紫龍戟 / 七星刀、倚天劍 / 方天畫戟、丈八蛇矛、青龍偃月刀 |
| +16 / +20 | 干將、莫邪 / **奧汀神槍（上限）** |

**推论**：基础武力 ≥ `80 − 20 = 60` 的武将，理论上都能靠武器跨过门槛 —— 这覆盖了原版绝大多数武将。

### 2.4 必杀技有两个独立来源（关键区分）

原版有 **16 名武将基础武力低于 80 却自带必杀技**，例如：

| 武将 | 基础武力 | 必杀技 |
|---|---|---|
| 李儒 | 42 | 7 |
| 天香 | 57 | 7 |
| 張寧 | 65 | 4 |
| 龐統 | 66 | 7 |
| 曹性 | 68 | 6 |
| 全端 / 潘鳳 | 75 | 5 / 2 |
| 周瑜 | 78 | 4 |
| 陸抗 / 金環三結 | 78 | 1 / 3 |
| 趙葳 | 79 | 5 |

这些人**不可能通过「攻击力 ≥ 80」学到**，只能是**开局预设**。因此：

> **必杀技来源 = ① 开局预设（`General01.ini : SuperAttack` 字段）+ ② 运行时达标自动学习**

原版的问题是：**②只对电脑方生效，我方被跳过** —— 这就是用户第 4 项需求要修的。

## 三、规则定义（引擎实现规范）

```yaml
rule_id: super_attack_learn
trigger: on_attack_changed          # 攻击力变化时求值（装备变更 / 入队 / 其他来源）
condition:
  current_attack_gte: 80            # 当前攻击力 >= 80
  exclude_beast: true               # 排除野兽
  not_already_known: true           # 尚未拥有（避免重复授予）
action:
  grant_super_attack: true
applies_to: [player_forces, ai_forces]   # 双方一致（原版只对电脑方生效）

# 方向性：只增不减。攻击力回落时不撤销（见 3.2）
monotonic: true
```

### 3.1 野兽判定（结构化规则，不用名字黑名单）

```yaml
beast_rule: intelligence <= 20 and hp >= 150
```

| 规则 | 命中 | 结论 |
|---|---|---|
| 智力 ≤ 20 | 6 条 | ✗ 误伤真人武将 `兀突骨(智18)`、`金環三結(智16)` |
| HP ≥ 150 | 4 条 | 正确但维度单一 |
| **智力 ≤ 20 且 HP ≥ 150** | **4 条** | ✅ 恰好命中 4 只野兽，零误伤 |

命中的 4 只：猛虎(武85/智12/HP150)、白額虎(94/10/240)、南蠻象(84/15/180)、印度神象(96/16/250)。

`黃巾頭目(智36/HP85)`、`黃巾將軍(智57/HP90)` 自动落在人形一侧 —— 与用户口径一致（黄巾头目/将军属人形武将，正常发必杀技）。

> 用户已决定：野兽不发必杀技，**后续另行设计特殊攻击方式**（二期项目）。

### 3.2 攻击力回落时的处理：**保留**（用户已确认）

**已学会的必杀技，在攻击力回落到 80 以下（例如卸下武器、武器被夺、武器被卖）后，保留不收回。**

用户口径（2026-09-13 确认）：「攻击力回落保留已学习的必杀技。」

理由与实现约束：

| 项 | 说明 |
|---|---|
| 语义 | 学习是**历史事件**，不是持续状态。学会的是「这个人会这招」，不是「因为他现在拿着刀所以他才会」 |
| 与需求③的关系 | 与「必杀技携带无上限」共用同一数据结构，不存在容量冲突 |
| 实现 | 授予时**只写不删**：`on_attack_changed` 只做「是否授予」的判断，**没有任何撤销分支** |
| 反例（不做） | 不实现「攻击力 < 80 则移除」的逻辑 —— 那会导致卸下武器时技能凭空消失，玩家无法理解 |

```yaml
on_deattack:                 # 攻击力回落时的行为
  revoke_super_attack: false # 明确禁止收回
  keep_granted: true         # 已授予的技能永久保留
```

> 若未来需要「临时增益型必杀技」（如某件宝物在装备期间才可用），那属于**另一种机制**
> （临时期限技能），与本条规则不冲突，另行设计，不复用本规则的字段。

## 四、引擎中的落点

| 层 | 模块 | 职责 |
|---|---|---|
| 数据 | `tools/build_data.py` → `generals.json` | 输出 `strength` / `weapon` / `weapon_bonus` / `current_attack` |
| 数据 | `tools/build_data.py` → `things.json` | 输出 `type` / `slot` / `increment` / `strength_bonus` |
| 数据 | `auto_superattack_targets.json` | 规则定义 + A/B/C 三类基准名单（**仅作回归测试用，不是补丁数据**） |
| 逻辑 | 武将属性系统 | `current_attack` 由「基础武力 + 装备加成」实时求值，**不缓存** |
| 逻辑 | 装备系统 | 任何装备变更 → 触发 `on_attack_changed` |
| 逻辑 | 必杀技系统 | 收到事件 → 校验条件 → 授予；与需求③的「无数量上限」共用同一数据结构 |
| 逻辑 | AI 势力 | 与玩家势力走**同一条规则**（消除原版的不对称） |

数据自检命令（可随时重跑，用于回归）：

```bash
python tools/build_data.py
```

## 五、待原版行为验证的两点（M3 阶段）

1. **自动学习时授予哪一个必杀技？** 8 种必杀技中如何选择？可能是随机、按武器类型、
   或按武力档位。需要逆向 `Script\SuperAttack.so`（已提取出符号 `SuperAttack01~08`、
   `SAisPossible`、`SAsetAct01/04`）或实机对照。
2. **电脑方原版判据究竟是「基础武力」还是「当前攻击力」？** 按用户口径，
   我们两边统一用「当前攻击力」；但逆向确认原版行为有助于判断改动幅度。

> 另注：原版 `SuperAttack` 字段**支持多值**（逗号分隔，如吕布 `5,8`），
> 说明「3 个上限」是代码层的显示/逻辑限制，不是数据格式限制 —— 与需求③的判断一致。

## 六、与其它需求的关系

| 需求 | 关联 |
|---|---|
| ③ 必杀技携带无上限 | 本规则与③共用同一套数据结构。解除 3 个上限后，「学满 8 种」不存在容量冲突 |
| ① 将领自动升级 | 若升级会改变武力（需确认），则升级也应触发 `on_attack_changed` |
| ② 士兵上限 1000 | 无直接关系 |
